# 文档维护约束

本目录由文档角色维护。代码实现子代理可以读取文档、核对契约并向主代理提出变更建议，不得直接创建、修改、移动或删除 `docs/**`。建议应说明现存行为、受影响的架构契约及依据；主代理决定是否纳入，再明确授权文档角色和可写路径。文档角色不得自行扩大写入范围。

## 内容要求

- 忠实描述当前架构：职责、状态所有权、模块关系、信任边界、生命周期和公开契约；未实现的方案不能写成现状。
- 文档用于指引读者到代码库找实现，不复制私有函数、算法、逐步调用图或测试清单。保留少量稳定的源码入口；公开参考可以保留必要的字段、限额和使用示例。
- 不把架构文档写成更新记录表，不追加“本次新增”、提交列表、版本流水账或合并进度。历史交给 Git 与发布说明；已有历史材料不作为现状权威，不擅自删除。
- 维护 `docs/README.md` 作为总导航，新增、移动或删除文档时同步入口和各目录简要说明。详细契约只在所属文档维护，避免多份说明竞争。
- 同一主题的 Markdown/HTML 同步更新；移除或替换失效表述，不保留相互矛盾的契约。检查链接和代码依据，不把静态核对写成线上验证。

## 权限边界

这些规则约束协作流程，不等于文件系统隔离。运行时应对代码角色将 `docs/` 设为只读，对文档角色仅开放主代理批准的文档范围；插件、项目 agent 配置和执行环境不能提供这种隔离时，必须明确报告，不能宣称已经形成硬权限。角色配置或提示词本身不授予写权限，也不能替代实际写入拒绝验证。
